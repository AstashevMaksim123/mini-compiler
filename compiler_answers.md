# Подробные ответы по проекту мини-компилятора

## 1. Как в коде реализованы правила грамматики? Что делает код с `$$` (semantic actions)?

### Общая идея

Правила грамматики реализованы в файле `src/parser.y`. Это файл для GNU Bison. В нём описывается формальная грамматика языка: какие последовательности токенов считаются корректной программой и как из них строится внутренняя структура программы.

Bison работает не просто как распознаватель текста, а как генератор синтаксического анализатора. Мы задаём:

- токены, которые приходят от лексера;
- нетерминалы грамматики;
- правила вывода;
- действия на C++, которые выполняются при свёртке правила.

Именно эти действия и называются `semantic actions`.

### Где это находится в проекте

Основная грамматика находится в:

- `src/parser.y`

Например, правило функции:

```bison
function:
    FN IDENT '(' params ')' ARROW type block {
        std::string name($2);
        free($2);
        $$ = new mini::FunctionDecl(makeRange(@$), name, *$4, $7, $8);
        delete $4;
    }
    ;
```

Это означает:

- если парсер увидел последовательность `fn`, затем идентификатор, затем список параметров, затем `->`, затем тип и блок;
- то это считается функцией;
- а в action-коде создаётся AST-узел `FunctionDecl`.

### Что такое `$1`, `$2`, `$3`, ... и `$$`

Внутри semantic actions Bison даёт специальную нотацию:

- `$1` — значение первого символа в правой части правила;
- `$2` — значение второго символа;
- `$3` — значение третьего;
- и так далее;
- `$$` — значение левой части правила, то есть результат свёртки.

Если говорить проще:

- `$1`, `$2`, ... — это входы;
- `$$` — это выход.

### Пример на простом выражении

```bison
additive:
    additive '+' multiplicative { $$ = new mini::BinaryExpr(makeRange(@$), "+", $1, $3); }
    | additive '-' multiplicative { $$ = new mini::BinaryExpr(makeRange(@$), "-", $1, $3); }
    | multiplicative { $$ = $1; }
    ;
```

Здесь:

- в первом правиле `$1` — уже разобранное левое выражение;
- `$3` — правое выражение;
- `$$` получает новый узел `BinaryExpr`, представляющий `lhs + rhs`.

То есть парсер не вычисляет выражение, а строит дерево:

- узел операции `+`;
- левый потомок — `$1`;
- правый потомок — `$3`.

### Почему это называется semantic action

Грамматика сама по себе отвечает только на вопрос:

- корректна ли последовательность токенов с точки зрения синтаксиса.

Semantic action отвечает уже на второй вопрос:

- что мы хотим сделать, когда такая конструкция встретилась.

В данном проекте semantic actions:

- создают AST-узлы;
- собирают списки параметров, выражений и операторов;
- прикрепляют source location;
- передают результат наверх через `$$`.

Важно, что в этом проекте действия парсера не генерируют LLVM IR напрямую. Это сознательное архитектурное решение. Парсер только строит AST.

### Почему AST строится именно в parser.y

Потому что парсер уже знает структуру программы:

- где начинается функция;
- где выражение;
- где оператор `if`;
- где тело `switch`;
- где блок и его границы.

Лексер этого не знает, он видит только поток токенов.

### Как реализованы списки

Для списков используются промежуточные векторы. Например:

```bison
function_list:
    function {
        $$ = new std::vector<mini::FunctionDecl*>();
        $$->push_back($1);
    }
    | function_list function {
        $1->push_back($2);
        $$ = $1;
    }
    ;
```

Первый вариант создаёт новый список, второй добавляет элемент в существующий список.

Это очень типичный паттерн для Bison:

- стартовый случай создаёт контейнер;
- рекурсивный случай его наращивает;
- `$$` возвращает уже обновлённый контейнер.

### Как используются location-метки

В grammar actions активно используется:

- `@$` — диапазон текущего правила;
- `@1`, `@2`, ... — диапазоны соответствующих символов.

В проекте есть helper `makeRange(...)`, который переводит Bison location в собственный `mini::SourceRange`. Затем этот range сохраняется в AST-узле.

Это нужно для качественной диагностики:

- синтаксических ошибок;
- семантических ошибок;
- ошибок codegen, если понадобится сослаться на исходный код.

### Что происходит после завершения разбора

В верхнем правиле `program` создаётся итоговый AST:

```bison
program:
    function_list {
        ctx.program = std::make_unique<mini::Program>(*$1);
        delete $1;
    }
    ;
```

Здесь результат разбора помещается в `ParserContext`.

Именно затем дальнейшие стадии компилятора получают доступ к AST:

- сначала `SemanticAnalyzer`;
- потом `CodeGenerator`.

### Почему `$$` важен

Если совсем коротко, `$$` — это способ передать результат разбора данного правила дальше наверх по дереву грамматики.

Без `$$` парсер мог бы только сказать:

- программа синтаксически верна;

но не смог бы построить структурированное представление программы.

Именно через `$$` происходит постепенное построение дерева:

- литерал становится `IntLiteralExpr`;
- выражения становятся `BinaryExpr` и `UnaryExpr`;
- инструкции становятся `Stmt`;
- блоки становятся `BlockStmt`;
- функции становятся `FunctionDecl`;
- вся программа становится `Program`.

## 2. Как и где происходит генерация кода под целевую платформу?

### Разделение стадий

Генерация машинно-ориентированного результата в проекте разбита на две стадии:

1. AST -> LLVM IR
2. LLVM IR -> объектный файл `.o` под целевую платформу

Это важное разделение.

Первая стадия находится в:

- `src/codegen.cpp`

Вторая стадия находится в:

- `src/object_emitter.cpp`

### Стадия 1: генерация LLVM IR

Класс `mini::CodeGenerator` обходит AST и создаёт IR-модуль LLVM.

Для этого используются:

- `llvm::LLVMContext`
- `llvm::Module`
- `llvm::IRBuilder<>`

Основная точка входа:

- `CodeGenerator::generate(const Program&, std::string&)`

Что происходит внутри:

- объявляются все функции модуля;
- для каждой функции создаётся `llvm::Function`;
- для тела функции создаются `BasicBlock`;
- для локальных переменных создаются `alloca`;
- для чтения и записи переменных используются `load/store`;
- для выражений строятся инструкции `add/sub/mul/sdiv/srem`, `icmp`, `and`, `or`, `not`;
- для `if`, `for`, `switch` создаются ветвления и переходы.

### Где задаётся target triple

В `CodeGenerator` конструктор получает целевой triple:

```cpp
CodeGenerator::CodeGenerator(std::string moduleName, std::string targetTriple)
```

И сразу сохраняет его в LLVM module:

```cpp
module_->setTargetTriple(targetTriple_);
```

По умолчанию target triple задаётся в `src/driver.cpp`:

```cpp
std::string targetTriple = "x86_64-pc-linux-gnu";
```

Но пользователь может переопределить его через:

```bash
--target x86_64-pc-linux-gnu
```

### Как генерируются функции

Сначала все функции объявляются в модуле, чтобы можно было поддержать вызовы между функциями и рекурсию.

Это делается в:

- `CodeGenerator::declareFunctions`

Там строится `llvm::FunctionType`, после чего вызывается:

```cpp
llvm::Function::Create(...)
```

Для `compiled_fn` выставляется `ExternalLinkage`, чтобы символ был виден снаружи и мог быть вызван из `runtime/main.c`.

### Как генерируются локальные переменные

Локальные переменные создаются в entry block функции через helper:

- `createEntryBlockAlloca(...)`

Это соответствует хорошей практике LLVM:

- все `alloca` удобно размещать в начале функции;
- это упрощает дальнейшие оптимизации и делает IR более аккуратным.

После этого:

- инициализатор вычисляется как `llvm::Value*`;
- затем выполняется `CreateStore`.

### Как генерируется `if / else`

Для `if` создаются basic blocks:

- `if.then`
- `if.else`
- `if.end`

Потом:

- условие вычисляется;
- создаётся `CreateCondBr(condition, thenBlock, elseOrEndBlock)`;
- генерируется код для веток;
- если ветка не закончилась `return` или `break`, добавляется переход в merge block.

### Как генерируется `for`

Для цикла создаются блоки:

- `for.cond`
- `for.body`
- `for.step`
- `for.end`

Схема такая:

1. генерируется init;
2. безусловный переход в `for.cond`;
3. в `for.cond` вычисляется условие;
4. если условие истинно, переходим в `for.body`, иначе в `for.end`;
5. после тела переходим в `for.step`;
6. после step снова идём в `for.cond`.

### Как генерируется `switch`

Это одна из центральных особенностей варианта.

Для него используется:

- `llvm::SwitchInst`

В `emitStmt` создаётся:

- вычисление switch-значения;
- конечный блок `switch.end`;
- при наличии `default` отдельный default block;
- по одному `BasicBlock` на каждый `case`.

Затем:

- `CreateSwitch(...)` создаёт switch-инструкцию;
- каждый `case` добавляется через `addCase(...)`;
- для каждого case генерируется тело блока;
- если case не завершился `return` или `break`, добавляется переход в `switch.end`.

Важное правило проекта:

- fallthrough не поддерживается;
- каждый case изолирован как отдельный блок.

### Как генерируется `break` и `continue`

Для этого в `CodeGenerator` есть стеки:

- `breakTargets_`
- `continueTargets_`

Когда мы входим:

- в цикл, на стек `break` кладётся `for.end`, а на стек `continue` кладётся `for.step`;
- в `switch`, на стек `break` кладётся `switch.end`.

Тогда:

- `break` всегда переходит в верхнюю breakable-цель;
- `continue` всегда переходит в верхнюю loop-цель.

Это особенно важно для вложенных конструкций, например:

- `switch` внутри `for`;
- `if` внутри `switch`;
- циклы внутри циклов.

### Стадия 2: выпуск объектного файла под платформу

Эта часть находится в `src/object_emitter.cpp`.

Функция:

- `emitObjectFile(llvm::Module&, const std::string&, std::string&)`

именно она превращает IR-модуль в настоящий `.o`.

### Какие LLVM-компоненты для этого используются

Сначала инициализируется инфраструктура target backend:

- `InitializeAllTargetInfos()`
- `InitializeAllTargets()`
- `InitializeAllTargetMCs()`
- `InitializeAllAsmParsers()`
- `InitializeAllAsmPrinters()`

Потом по target triple ищется backend:

```cpp
const llvm::Target* target = llvm::TargetRegistry::lookupTarget(targetTriple, lookupError);
```

После этого создаётся:

- `TargetMachine`

именно он знает, как отображать LLVM IR в машинно-ориентированный код для конкретной платформы.

### Что делает TargetMachine

`TargetMachine` инкапсулирует знания о:

- архитектуре процессора;
- ABI;
- размере и выравнивании типов;
- формате объектного файла;
- соглашениях вызова;
- способах выбора инструкций.

В проекте он создаётся примерно так:

```cpp
target->createTargetMachine(targetTriple, "generic", "", options, llvm::Reloc::PIC_)
```

Далее его `DataLayout` записывается в module:

```cpp
module.setDataLayout(targetMachine->createDataLayout());
```

### Как реально создаётся `.o`

Далее используется `legacy::PassManager` и метод:

```cpp
targetMachine->addPassesToEmitFile(...)
```

То есть LLVM строит цепочку backend-pass'ов, которые:

- проводят instruction selection;
- учитывают target-specific lowering;
- формируют машинный код;
- сериализуют его в ELF object file.

Затем:

```cpp
passManager.run(module);
```

И на диск записывается настоящий объектный файл.

### Где это всё запускается из CLI

В `src/driver.cpp`:

1. входной файл разбирается;
2. проходит семантический анализ;
3. генерируется LLVM IR;
4. при `--emit-ir` сохраняется `.ll`;
5. вызывается `emitObjectFile(...)`.

Именно здесь связываются все стадии компилятора в единый pipeline.

## 3. Объясните роль Flex/re2c и Bison в проекте

### Роль Flex

Flex отвечает за лексический анализ.

Он получает на вход простой текст программы и превращает его в поток токенов.

Примеры токенов:

- ключевое слово `fn`
- идентификатор `compiled_fn`
- литерал `10`
- оператор `==`
- скобка `{`
- разделитель `;`

То есть Flex решает задачу:

- разбить поток символов на осмысленные лексические единицы.

В этом проекте лексер реализован в:

- `src/lexer.l`

### Что делает лексер на практике

Лексер:

- пропускает пробелы и комментарии;
- распознаёт числа;
- распознаёт имена;
- отличает ключевые слова от обычных идентификаторов;
- возвращает токены парсеру;
- заполняет `yylval`, если у токена есть значение;
- заполняет `yylloc`, чтобы сохранить line/column.

Например:

- для `123` лексер возвращает `INT_LITERAL` и кладёт само число в `yylval.int_val`;
- для `abc` лексер возвращает `IDENT` и кладёт строку в `yylval.str`.

### Почему без лексера неудобно

Парсеру сложно работать напрямую с символами. Ему намного удобнее получать уже абстрактные единицы:

- не `'f' 'n'`, а токен `FN`;
- не последовательность цифр, а `INT_LITERAL`.

Это резко упрощает grammar rules.

### Роль Bison

Bison отвечает за синтаксический анализ.

Он получает поток токенов от Flex и проверяет, соответствует ли он грамматике языка.

Если соответствует, Bison:

- вызывает semantic actions;
- строит AST.

Если не соответствует, Bison:

- сигнализирует о синтаксической ошибке;
- запускает механизм `yyerror`.

### Как Flex и Bison взаимодействуют

Связка такая:

1. Flex читает символы из файла.
2. Flex возвращает Bison токены.
3. Bison по grammar rules решает, как сворачивать токены и нетерминалы.
4. В semantic actions создаются AST-узлы.

Иначе говоря:

- Flex отвечает на вопрос "что это за кусок текста?";
- Bison отвечает на вопрос "как эти куски текста составляют корректную программу?".

### Почему в проекте выбран именно этот стек

Потому что для учебного компилятора это классический и очень подходящий вариант:

- хорошо демонстрирует разделение лексики и синтаксиса;
- позволяет явно задать грамматику;
- помогает показать приоритеты операций;
- удобно дополняется semantic actions;
- хорошо сочетается с последующим построением AST и LLVM backend.

### А где здесь re2c

В этом проекте `re2c` не используется. Он упоминается как допустимая альтернатива, но фактически выбран именно Flex.

Причина выбора:

- Flex проще интегрировать в стандартный учебный pipeline вместе с Bison;
- для курсовой работы он даёт более прямолинейную и наглядную реализацию.

## 4. Зачем нужен файл с кодом абстрактного синтаксического дерева?

### Что такое AST

AST, или Abstract Syntax Tree, — это структурированное представление программы в виде дерева.

Оно отражает смысловую структуру кода, но убирает лишние поверхностные детали текста.

Например, выражение:

```rust
x + 2 * y
```

в AST становится не строкой, а деревом:

- корень `+`
- слева `x`
- справа `*`
  - слева `2`
  - справа `y`

### Где AST описан в проекте

- `include/ast.hpp`
- `src/ast.cpp`

### Почему AST — отдельный слой, а не всё сразу в parser.y

Потому что AST отделяет:

- разбор синтаксиса;
- семантический анализ;
- генерацию кода.

Это ключевое архитектурное преимущество.

Если бы парсер сразу генерировал LLVM IR:

- логика быстро стала бы запутанной;
- семантические проверки пришлось бы встраивать в parser actions;
- поддержка новых конструкций была бы существенно сложнее.

### Что даёт AST практически

AST позволяет:

- один раз корректно распарсить программу;
- затем несколько раз обойти её разными проходами;
- хранить информацию о расположении в исходнике;
- дописывать новые анализаторы и трансформации.

В этом проекте AST используется минимум в двух больших фазах:

1. семантический анализ;
2. генерация LLVM IR.

### Какие узлы есть в AST

В проекте есть:

- `Program`
- `FunctionDecl`
- `BlockStmt`
- `VarDeclStmt`
- `AssignStmt`
- `IfStmt`
- `ForStmt`
- `SwitchStmt`
- `CaseClause`
- `ReturnStmt`
- `BreakStmt`
- `ContinueStmt`
- `ExprStmt`
- `IntLiteralExpr`
- `BoolLiteralExpr`
- `VarExpr`
- `UnaryExpr`
- `BinaryExpr`
- `CallExpr`

Такой набор делает AST близким к структуре самого языка.

### Почему это удобно для семантики

Семантическому анализатору важно понимать именно смысл конструкции.

Например:

- `VarDeclStmt` означает объявление новой переменной;
- `AssignStmt` означает присваивание;
- `SwitchStmt` означает проверку case-значений и default;
- `BreakStmt` требует знания контекста цикла или switch.

Без AST пришлось бы заново восстанавливать смысл из более низкоуровневых структур.

### Почему это удобно для codegen

Codegen обходит AST и для каждого типа узла знает, какой IR строить.

Например:

- `IfStmt` -> условное ветвление;
- `ForStmt` -> четыре basic block;
- `BinaryExpr` -> арифметическая или логическая инструкция LLVM;
- `ReturnStmt` -> `CreateRet`.

AST тем самым является центральным промежуточным представлением между frontend и backend.

## 5. Как реализован приоритет арифметических операций?

### Общая идея

Приоритет операций реализован в grammar rules Bison.

Это один из самых важных моментов в любом парсере выражений: нужно сделать так, чтобы:

```rust
1 + 2 * 3
```

разбиралось как:

```text
1 + (2 * 3)
```

а не как:

```text
(1 + 2) * 3
```

### Где это сделано

В `src/parser.y` есть секция объявлений приоритетов:

```bison
%left OROR
%left ANDAND
%left EQ NE
%left '<' '>' LE GE
%left '+' '-'
%left '*' '/' '%'
%right UMINUS '!'
```

Эти строки задают:

- порядок приоритетов;
- ассоциативность.

### Как читать эти объявления

В Bison объявления идут от меньшего приоритета к большему.

То есть:

1. `||`
2. `&&`
3. `==`, `!=`
4. `<`, `<=`, `>`, `>=`
5. `+`, `-`
6. `*`, `/`, `%`
7. унарные `-` и `!`

Это соответствует стандартной математической и языковой интуиции.

### Как это связано с правилами выражений

Кроме `%left/%right`, грамматика ещё и структурно разбита на уровни:

- `logical_or`
- `logical_and`
- `equality`
- `relational`
- `additive`
- `multiplicative`
- `unary`
- `primary`

Например:

```bison
additive:
    additive '+' multiplicative
    | additive '-' multiplicative
    | multiplicative
    ;
```

и:

```bison
multiplicative:
    multiplicative '*' unary
    | multiplicative '/' unary
    | multiplicative '%' unary
    | unary
    ;
```

За счёт этого `multiplicative` вкладывается глубже, чем `additive`, и поэтому связывается сильнее.

### Зачем ещё нужен `%prec UMINUS`

Символ `-` может быть:

- бинарным: `a - b`
- унарным: `-x`

Чтобы унарный минус имел отдельный приоритет, используется:

```bison
'-' unary %prec UMINUS
```

То есть этому правилу назначается приоритет фиктивного токена `UMINUS`.

Это стандартный способ разрулить неоднозначность унарного и бинарного минуса в Bison.

### Что получилось в итоге

В результате выражения разбираются корректно:

- `1 + 2 * 3`
- `a < b && c != d`
- `!(x == 0) || y > 10`
- `-(a + b) * c`

И уже на этом корректном дереве затем работает семантика и codegen.

## 6. Что поддерживает семантический анализ в вашем проекте?

Семантический анализ реализован в:

- `include/sema.hpp`
- `src/sema.cpp`

Его задача — проверить не только форму программы, но и её смысловую корректность.

### 1. Проверка функций

Сначала собирается таблица функций:

- имя функции;
- тип возвращаемого значения;
- типы параметров.

Проверяется:

- отсутствие дублирующихся имён функций;
- наличие обязательной функции `compiled_fn`;
- соответствие её сигнатуры контракту:

```rust
fn compiled_fn(arg: int) -> int
```

### 2. Проверка областей видимости

Семантика ведёт стек scopes:

- каждая область видимости — это отдельная таблица переменных;
- при входе в блок создаётся новый scope;
- при выходе — удаляется.

Это позволяет корректно поддержать:

- вложенные блоки;
- затенение переменных во внутренних блоках;
- запрет повторного объявления в одной и той же области.

### 3. Проверка объявлений переменных

Проверяется:

- что переменная не объявлена повторно в том же scope;
- что инициализатор имеет совместимый тип;
- что при присваивании переменная уже существует;
- что она mutable, если в неё идёт запись.

### 4. Проверка типов выражений

Для каждого выражения вычисляется `inferredType`.

Поддерживается строгая система типов:

- `int`
- `bool`

Проверки:

- арифметика требует `int`;
- сравнения `< <= > >=` требуют `int`;
- `==` и `!=` требуют одинаковые типы слева и справа;
- `&&` и `||` требуют `bool`;
- `!` требует `bool`;
- унарный `-` требует `int`.

### 5. Проверка условий

Проверяется, что:

- условие `if` имеет тип `bool`;
- условие `for` имеет тип `bool`.

Это предотвращает неявные преобразования в стиле C.

### 6. Проверка switch

Это одна из ключевых частей семантики варианта.

Проверяется:

- выражение `switch` имеет тип `int`;
- каждый `case` содержит целочисленный литерал;
- внутри одного `switch` нет повторяющихся case-значений;
- `default` встречается не более одного раза.

### 7. Проверка return

Проверяется:

- что тип возвращаемого выражения совпадает с типом функции;
- что функция возвращает значение по всем путям исполнения.

Для второй задачи используется анализ вида:

- `return` всегда завершает путь;
- блок always-returns, если один из его операторов гарантированно завершает выполнение;
- `if` always-returns, если обе ветки always-return;
- `switch` always-returns, если есть `default` и все case-блоки always-return.

### 8. Проверка break/continue

Семантика хранит глубину:

- циклов;
- switch-конструкций.

Проверяется:

- `break` разрешён только внутри цикла или `switch`;
- `continue` разрешён только внутри цикла.

### 9. Проверка вызовов функций

Для `CallExpr` проверяется:

- что функция существует;
- что количество аргументов совпадает;
- что типы аргументов соответствуют сигнатуре.

### 10. Диагностика

Все найденные ошибки собираются в `ParserContext::diagnostics`.

Каждая ошибка содержит:

- диапазон в исходном коде;
- понятное текстовое сообщение.

Примеры:

- `line 3:12: variable 'x' is not declared`
- `line 5:8: if condition must have type bool`
- `line 10:5: duplicate case value 3`

То есть семантический анализ в проекте покрывает основные проверки корректности, которые ожидаются от учебного компилятора.

## 7. Как обрабатываются ошибки синтаксиса?

### Где они возникают

Синтаксические ошибки возникают в момент работы Bison-парсера, если поток токенов от Flex не соответствует grammar rules.

Например:

- пропущена `;`
- пропущена `}`
- неожиданно встретился `else`
- неправильная форма `switch`
- сломан заголовок функции

### Как это реализовано

В `src/parser.y` задано:

```bison
%define parse.error detailed
```

Это просит Bison формировать более содержательные сообщения, чем простое `syntax error`.

Также внизу файла определена функция:

```cpp
void yyerror(mini::ParserContext& ctx, const char* msg) {
    ctx.report(makeRange(yylloc), msg);
}
```

Она вызывается парсером, когда обнаруживается синтаксическая ошибка.

### Что делает yyerror

`yyerror`:

- берёт текущую позицию `yylloc`;
- переводит её в `SourceRange`;
- складывает диагностическое сообщение в `ParserContext`.

То есть ошибка не просто печатается немедленно в stdout/stderr, а аккуратно сохраняется в общей диагностической системе проекта.

### Как координаты доходят до yyerror

Лексер в `src/lexer.l` обновляет `yylloc` через `YY_USER_ACTION`.

Там ведутся:

- `lexer_line`
- `lexer_column`

Для каждого токена фиксируются:

- начало;
- конец.

За счёт этого сообщение об ошибке может ссылаться на конкретное место в исходнике.

### Что происходит в драйвере

В `src/driver.cpp` после вызова:

```cpp
yyparse(context)
```

проверяется:

- вернул ли парсер ошибку;
- есть ли diagnostics;
- построен ли `context.program`.

Если нет, компиляция завершается с ненулевым кодом возврата, а собранные сообщения печатаются пользователю.

### Какой формат ошибки видит пользователь

Проект форматирует диагностику так:

```text
line <line>:<column>: <message>
```

Например:

```text
line 4:7: syntax error, unexpected ELSE, expecting ';'
```

Конкретный текст зависит от того, что именно вернёт Bison.

### Что проект делает после синтаксической ошибки

После такой ошибки дальнейшие стадии:

- семантический анализ;
- codegen;
- выпуск `.o`

не запускаются.

Это важно, потому что без корректного AST дальнейшая обработка не имеет смысла.

### Почему это хороший подход

Потому что:

- синтаксические ошибки локализуются максимально рано;
- пользователь получает координаты;
- система диагностики единая как для parser, так и для sema;
- backend не пытается работать по некорректному дереву.

## 8. В чём смысл LLVM IR и общие принципы его построения?

### Что такое LLVM IR

LLVM IR — это промежуточное представление программы, находящееся между исходным языком и машинным кодом.

Его смысл в том, чтобы:

- отделить frontend от backend;
- иметь удобную и формальную форму программы для анализа;
- облегчить перенос на разные архитектуры;
- использовать готовую экосистему LLVM для оптимизаций и генерации объектного кода.

Проще говоря:

- наш язык не знает, как устроен x86_64;
- backend LLVM знает;
- LLVM IR служит мостом между ними.

### Почему не генерировать сразу x86 assembly

Сразу генерировать ассемблер можно, но для учебного компилятора это быстро приводит к проблемам:

- нужно вручную реализовывать соглашения вызовов;
- нужно управлять регистрами;
- нужно учитывать ABI;
- сложнее поддерживать переносимость;
- сложнее расширять язык.

LLVM IR позволяет этого избежать.

### Какие свойства есть у LLVM IR

LLVM IR:

- строго типизирован;
- SSA-ориентирован;
- состоит из функций, basic blocks и инструкций;
- независим от конкретной архитектуры на frontend-уровне;
- хорошо проверяется verifier'ом.

### Как мы строим IR в проекте

Построение идёт сверху вниз по AST.

Сначала создаётся:

- `LLVMContext`
- `Module`
- `IRBuilder`

Дальше:

- каждая функция AST становится `llvm::Function`;
- каждое выражение становится `llvm::Value*`;
- каждый оператор создаёт набор инструкций или ветвлений.

### Базовые принципы построения IR

#### 1. Каждый AST-узел переводится в свою IR-форму

Например:

- `IntLiteralExpr` -> `ConstantInt`
- `BoolLiteralExpr` -> `ConstantInt(i1)`
- `BinaryExpr(+)` -> `CreateAdd`
- `BinaryExpr(<)` -> `CreateICmpSLT`
- `ReturnStmt` -> `CreateRet`

#### 2. Управляющие конструкции переводятся в CFG

LLVM IR выражает управление не через высокоуровневые слова `if` или `for`, а через:

- `BasicBlock`
- `br`
- `condbr`
- `switch`

Поэтому:

- `if` превращается в ветвление;
- `for` превращается в цикл из нескольких basic blocks;
- `switch` превращается в `SwitchInst`.

#### 3. Переменные хранятся через alloca/load/store

В этом проекте выбран простой и надёжный путь:

- локальные переменные выделяются через `alloca`;
- запись идёт через `store`;
- чтение идёт через `load`.

Это не максимальная оптимальность, но очень хорошая стратегия для учебного компилятора.

LLVM при желании потом может продвинуть значения ближе к SSA-форме оптимизационными pass'ами.

#### 4. Типы исходного языка должны соответствовать типам LLVM

В проекте:

- `int` -> `i64`
- `bool` -> `i1`

Поэтому генератор всегда обязан знать тип выражения заранее. Именно поэтому sema идёт раньше codegen.

#### 5. IR должен быть валидным

После генерации каждой функции вызывается:

- `verifyFunction`

После генерации всего модуля:

- `verifyModule`

Verifier проверяет:

- согласованность типов;
- корректность переходов между блоками;
- наличие терминаторов;
- общую структурную корректность IR.

Это очень важный защитный механизм.

### Чем IR полезен в проекте практически

LLVM IR даёт сразу несколько преимуществ:

- легко сохранить `.ll` и посмотреть, что именно сгенерировал компилятор;
- удобно отлаживать codegen;
- просто получить `.o` для `x86_64` без ручной генерации ELF;
- обеспечивается корректное соглашение вызова для `compiled_fn`.

### Почему IR особенно полезен для switch/for/if

Эти конструкции хорошо ложатся на CFG.

Например:

- `if` = условный выбор следующего блока;
- `for` = цикл с обратным ребром к condition block;
- `switch` = многостороннее ветвление по одному значению.

LLVM IR идеально подходит для такого представления, потому что basic blocks и переходы являются его базовыми строительными элементами.

### Общий смысл в контексте курсовой

LLVM IR в этом проекте — это центральный мост между frontend и machine backend.

Frontend решает:

- что значит программа.

LLVM backend решает:

- как это выполнить на `x86_64 Linux`.

IR нужен именно для того, чтобы эти две части были независимыми, чистыми по архитектуре и при этом хорошо состыкованными.
